# Voltmart Orders ETL Pipeline

An end-to-end data engineering pipeline that cleans, transforms, and loads
e-commerce order data for analytics and demand-forecasting use cases.

## Business context

Voltmart, an electronics e-commerce company, needs its raw order data
cleaned and structured before it can be used to build a demand-forecasting
model and answer basic business questions (top categories, revenue by
state, order patterns by time of day).

This pipeline takes the raw, messy `orders_data.parquet` export and turns
it into a clean, query-ready table.

## Architecture

```
Raw data (parquet)
        │
        ▼
┌───────────────────┐
│  1. TRANSFORM      │   src/transform.py   (PySpark)
│  - clean nulls/    │
│    inconsistencies │
│  - derive columns  │
│  - filter bad rows │
└─────────┬──────────┘
          ▼
  Clean data (parquet)
          │
          ▼
┌───────────────────┐
│  2. LOAD           │   src/load.py        (DuckDB)
│  - load into SQL   │
│    warehouse table │
└─────────┬──────────┘
          ▼
┌───────────────────┐
│  3. ANALYZE        │   sql/analysis_queries.sql
│  - business SQL    │
│    queries         │
└────────────────────┘
```

Each stage is a standalone script, so the pipeline can be lifted into a
proper orchestrator (Airflow / Prefect / Dagster) as a DAG with minimal
changes — `run_pipeline.py` currently orchestrates the stages sequentially
to keep the project runnable with zero extra infrastructure.

## Tech stack

- **Python** — pipeline logic and orchestration
- **PySpark** — distributed data cleaning/transformation
- **DuckDB** — lightweight SQL warehouse (drop-in swap for Snowflake /
  BigQuery / Redshift in production)
- **SQL** — business analysis queries

## Cleaning logic

| Column | Transformation |
|---|---|
| `order_date` | Removed orders placed 12am–5am (inclusive); cast from timestamp to date |
| `time_of_day` | New column: "morning" (5am–12pm), "afternoon" (12pm–6pm), "evening" (6pm–12am) |
| `product` | Lowercased; rows containing "tv" removed (discontinued product line) |
| `category` | Lowercased |
| `purchase_state` | New column: US state abbreviation extracted from `purchase_address` |

## Results

- **185,950** raw orders → **170,921** clean orders after filtering
- **8** unique US states represented in the cleaned data
- Data validated and loaded into a queryable `orders` table

## Setup

```bash
git clone <your-repo-url>
cd orders-pipeline
python -m venv venv
source venv/bin/activate       # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

You'll also need Java 8/11/17 installed (required by PySpark).

## Running the pipeline

Run the full pipeline (transform → load):

```bash
cd src
python run_pipeline.py
```

Or run stages individually:

```bash
python src/transform.py    # cleans raw data -> data/processed/orders_data_clean.parquet
python src/load.py         # loads clean data -> data/processed/orders.duckdb
```

## Running the analysis queries

```bash
duckdb data/processed/orders.duckdb < sql/analysis_queries.sql
```

Or interactively:

```bash
duckdb data/processed/orders.duckdb
```
```sql
SELECT category, SUM(turnover) AS revenue
FROM orders
GROUP BY category
ORDER BY revenue DESC;
```

## Dashboard

A Streamlit dashboard sits on top of the DuckDB warehouse for quick,
interactive exploration of the cleaned data — revenue by category/state,
order volume by time of day, daily order trend, and top products, with
sidebar filters for state/category/time of day.

Run it after the pipeline has produced `data/processed/orders.duckdb`:

```bash
streamlit run dashboard/app.py
```

## Continuous Integration

Every push/PR to `main` triggers a GitHub Actions workflow
(`.github/workflows/ci.yml`) that:

1. Installs dependencies (including Java, required by PySpark)
2. Lints the codebase with `ruff`
3. Runs the pipeline smoke tests (`pytest tests/`), which actually
   execute the transform and load stages against the raw data and
   assert the cleaning requirements are met (no night orders, no TV
   products, lowercase text, valid state codes, non-empty warehouse
   table)

This means every change to the pipeline is automatically verified before
it can be merged — the same pattern used in production data engineering
workflows.
